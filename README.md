# visually sorting embeddings — UI

The front end for
[visually sorting embeddings](https://git.krishnarajthadesar.in/krishnaraj/visually_sorting_embeddings):
a 3-D view of word vectors that shows its own error bars.

React 18, Vite, Tailwind v4, react-three-fiber. Deploys to Vercel and Netlify.

## Running it

```bash
npm install
npm run dev          # http://localhost:1186
```

`npm run dev` proxies `/api` to `http://localhost:1184`, so point it at a local
backend:

```bash
# in the backend repo
PORT=1184 .venv/bin/python main.py
```

Set `VITE_DEV_API` to proxy somewhere else, `VITE_API_BASE` to build against a
different backend than the default one (see below).

| Script | What it does |
|---|---|
| `npm run dev` | Vite dev server with the `/api` proxy |
| `npm run build` | Production build into `dist/` |
| `npm run preview` | Serve the built output |
| `npm run lint` | ESLint, warnings included |

## Demo mode

With no backend reachable the app runs off the precomputed bundle in
`public/demo` — 109 files, 2.0 MB, generated by `scripts/export_demo.py` in the
backend repo. This is what a visitor gets whenever the hosted API
is down or unreachable, and it is a real demo rather than a screenshot: every word
set, every method and every model is switchable, the similarities are the true
ones, and the cross-lingual measurements are there too — those are properties
of the model rather than of the picture, so shipping them as answers costs a
few kilobytes and loses nothing.

Two things it cannot do. It cannot embed a word you typed, because that needs a
model — so the input box disables itself and says so. And it cannot serve the
dimensions panel, which reads the raw vectors: the bundle ships cosine
similarities instead, which is why it is 2 MB rather than 90. Both report
themselves as unavailable with the reason, through `capabilities`, rather than
failing.

Mode is decided by probing `/api/meta` at startup with a 2.5 s timeout, not by
a build flag — the same deployed bundle therefore works with a backend, without
one, and with one that went down while the tab was open. Both backings return
identical shapes, so no component above [`lib/api.js`](src/lib/api.js) knows
which one it is talking to; the only difference it may observe is
`capabilities.canEmbed`.

## Deploying it

`.gitea/workflows/deploy.yml` deploys to **Netlify and Vercel** on every push to
`main`, and builds a preview of each on pull requests — the same two-job
workflow as the other UIs here. It needs these repository secrets:

| Secret | For |
|---|---|
| `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` | Vercel |
| `NETLIFY_TOKEN` | Netlify |

The Netlify job finds the site named after the repo
(`visually-sorting-embeddings-ui`) and creates it on the first run; the Vercel
job reads the commit metadata out of git so the dashboard shows the author and
message rather than a bare SHA. SPA fallback and cache headers are in
`vercel.json` for Vercel and `public/_redirects` and `public/_headers` for
Netlify — the same two rules in both.

### Where it finds the backend

Production builds talk to **`https://vsembeddings-api.krishnarajthadesar.in`**
([the backend repo](https://git.krishnarajthadesar.in/krishnaraj/visually_sorting_embeddings)
runs there), and nothing needs configuring in either dashboard. That URL is the
default in [`src/lib/api.js`](src/lib/api.js) rather than an environment
variable on purpose: Vercel builds the app remotely and the Netlify job builds
it on the runner, so a value that had to be set in both places would
eventually be missing from one.

| `VITE_API_BASE` | The build talks to |
|---|---|
| unset | the URL above (production); the Vite proxy (`npm run dev`) |
| a URL | that URL |
| set but empty | nothing — a demo-only build |

The backend allows any origin, so the Vercel and Netlify URLs, and every
preview URL, can call it with no allow-list to keep in step. It rate-limits
per client, and a visitor who hits the limit sees the server's message rather
than a broken page.

Because mode is decided at runtime (see [Demo mode](#demo-mode)), the site
stays up if the backend does not: it falls back to the precomputed bundle and
the header says **Precomputed** instead of **Live model**.

## The two surfaces

The 3-D view is a *window* into the model, not a page background — so it is a
dark vacuum, and the controls around it are a light instrument panel. Those two
colours are the same value, `#1a1a19`, used as ground on one side and as ink on
the other.

That value is not a decorative near-black. It is the dark chart surface that
every colour in the viewport was validated against for colour-blind separation
and 3:1 contrast, so the markers are known-legible rather than hopefully so.

## What the colours mean

The interface teaches exactly **one** colour association: darker blue means
more similar. The point cloud shades by similarity to the word you selected and
the matrix shades by pairwise similarity, both on the same seven-step blue
ramp — so a colour learned in one place reads correctly in the other. The
matrix is sequential rather than diverging for the same reason: a diverging
scale would need a second hue for its far pole and would end up putting
"similar" in red three inches from where it is blue.

Cluster colours stop at **three**, which is a measured limit rather than a
preference. A 3-D scatter is an all-pairs form — spin the camera and every
group eventually sits beside every other, so each *pair* of colours has to
survive on its own. Three do (worst pair ΔE 9.4 under deuteranopia, 20.9 in
normal vision). Six do not: no six-hue subset in the lightness band a dark
surface needs clears the colour-blind floor. So past three groups the app drops
colour rather than start repeating it, and marker **shape** carries the
grouping. The legend says so, because a user looking at six grey markers is
otherwise entitled to think something is broken.

The two cross-lingual colourings — **by language** and **by meaning** — inherit
that limit rather than arguing with it, which is why no word grid in the
backend has more than eight languages: eight is how many marker shapes there
are. They only appear for the concept-by-language word sets, because an
ordinary word list has no language or concept to colour by, and loading one
while that mode is active falls back to similarity rather than leaving the view
uniformly grey.

Flipping between those two is the whole argument in two clicks. On GloVe, *by
language* separates cleanly and *by meaning* does not — the clusters in that
space are languages. On LaBSE it is the other way round. The "Meaning or
language" panel on the right puts a number on what you are looking at, measured
on the full vectors, so it does not move when you change the projection method.

## Explaining itself

Every number on screen has a name that means nothing until someone tells you,
and a number whose definition the reader guesses at is worse than no number.
So the app ships 25 explanations across five topics, and they arrive from the
backend with everything else — `app/data/glossary.py` is the source, for the
same reason the presets do: the definition of trustworthiness belongs beside
the code that computes it.

They appear in two places, and the split is a constraint rather than a
preference. Both rails are `overflow-y-auto`, which clips any absolutely
positioned child, so a floating hover card would need a portal plus measuring
and flipping logic to survive in a 284px column. Instead a term is a button
with a dotted underline: hovering gives the browser's own tooltip, which is
never clipped, and clicking expands the sentence inline. Inline expansion also
works on touch, where hover does not exist — and a hover-only explanation on a
phone is no explanation.

The **reference list** at the bottom of the readout column has all of them with
the long form, grouped by topic and searchable. Grouped rather than
alphabetical because nobody looks up "stress" by its initial letter, and
alphabetical order would separate the two projection-quality measures that only
make sense read together.

## The screen

Three columns, and none of them collapses.

| Region | What is on it |
|---|---|
| Left rail | model, translate-first switch, word list, word sets, vector arithmetic |
| Viewport | the cloud, labels, neighbour edges |
| Method strip | the six projections, each keeping its score |
| Readout column | projection quality, meaning-or-language, dimensions, colour, every pair, extremes, reference |

The left rail is a permanent column rather than a drawer behind a button.
Which model you are looking at and which words are in it are not settings you
configure once and put away — they are the two variables of every comparison
the app exists to make, and the whole method is to change one and watch the
readouts on the right move. Behind a toggle that cost a click each way and
stopped being switchable at a glance.

The two rails are fixed widths and the viewport takes what is left, so
switching model or word set never shifts the plot sideways. Under 760px the
grid stops being a grid and the three stack, rail first.

### The method strip is a scoreboard

Switching projection is the point of the app, so the switch is not a dropdown.
It is a row across the foot of the viewport, and each method keeps the
trustworthiness it earned **on the current word set** once it has been run. Two
or three clicks in, the control has become a table of which flattenings survive
these particular words — a question you could not otherwise ask without writing
numbers down by hand. Scores clear whenever the words or the model change,
because a stale number under a method name would be the most convincing kind of
wrong.

### Axes appear for two methods only

PCA gets labelled axes with the variance each one accounts for. Raw mode gets
them because its axes literally are dimensions 41, 42 and 43. t-SNE, UMAP, MDS
and random projection get nothing: their layouts are defined only up to
rotation, so there is no "x" to label, and drawing a frame anyway is the
commonest way these plots mislead people. The absence is the signal.

### The one moment of motion

When the method changes, the points travel to their new coordinates instead of
cutting. That is not decoration — watching which words stay together and which
fly apart *is* the comparison between two methods, and it is the thing two
static screenshots cannot show. New words arrive from the origin so adding one
reads as an arrival. All of it respects `prefers-reduced-motion`.

### Labels declutter themselves

Words cluster, so their labels collide, and two overlapping words are less
readable than one word and a dot. Each label is projected to screen space and
claims a small box; nearer labels claim first, so the one in front wins — which
is also the correct depth cue. The selected and hovered words always win, since
a label that vanishes when you point at it is worse than a collision.

## Things worth clicking

- **Six unrelated fields** on GloVe, then flip along the whole method strip.
  Random projection scores 1% on distances; UMAP 67%. The difference between
  those two pictures is what the method contributed.
- **Words with two meanings** — watch `python` sit between the snakes and the
  programming, belonging to neither. It has one vector and two senses.
- **Opposites** — `hot` and `cold` come out as neighbours. Nothing is broken:
  they appear in the same sentences about the same things, and these models
  encode context, not truth.
- **Sentences, not words** on `openai-3-small`. All five paraphrase pairs rank
  as the five most similar pairs on screen. Then try the same set on GloVe,
  which has no vector for a sentence at all.
- Load **the same word in six languages**, colour by language, then by meaning,
  and switch the model from GloVe down to LaBSE. On GloVe the six languages
  come apart and the eight concepts do not; by LaBSE the eight concepts have
  become eight groups of six and the languages are nowhere. Then find the
  French `pain` — spelled like the English word for suffering, and the one
  point in the set where form and meaning disagree.
- Select a word, open **Dimensions**, and read the overlap column against the
  cosine column. `water` and `вода` drive all five of the same top dimensions;
  `book` and `livre` share one. Then switch the projection method to **raw**,
  set "Pick by" to *most varied*, and read what those three dimensions actually
  explain — 1.1% against PCA's 46.1%. The two panels are the two halves of the
  same answer: no single dimension means anything, and the combination is still
  partly legible.
- Flip the model switch to **translate to English** and watch every concept
  fuse into a single point. That is what a pivot index is: translation erases
  the language, and it erases the difference between six documents along with
  it. The panel on the right says so rather than reporting the perfect score.
- Select any word and read the two neighbour lists against each other. "Nearest
  on screen" is the words you plotted; "nearest in the model" is the whole
  50,000-word vocabulary, and it regularly contains something that changes your
  mind about the word.
